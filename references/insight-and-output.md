# Reference · 洞察提炼与报告输出（Phase 6 / 7 + 溯源契约）

取证与验证完成后，本文件指导如何提炼跨维度洞察、组装最终报告，并规定贯穿全程的溯源引用契约。

---

## Phase 6：洞察提炼

**目标**：识别**非显性**洞察——不直接出现在既有发现里，而是从跨维度比对中涌现。

**洞察定义**：由多条已验证发现推导出的更高阶推断，**不得重复**已陈述的主张或证据。

**流程**：
1. 复盘 Phase 3–5 的全部已验证发现（Route C/D 还含 Phase F 文件分析）。
2. 识别只有在比对多个维度时才可见的模式。
3. 提炼揭示以下之一的洞察：结构性关系、隐藏张力、新兴趋势、系统性风险、战略机会。
4. 确保每条洞察由**至少两个维度**的证据间接支撑。

**按路由侧重**：
- **Route C/D**：优先跨文件综合才显现的模式（单一文件看不出）；Route D 额外指出外部证据在何处强化/反驳/延伸了文件结论。
- **Route A**：优先桥接不同广探面向的洞察——独立探索的区域之间的连接。

**按目标文体调整**（下游写作格式）：
- **报告**（行研、市场分析、咨询交付）：优先可执行的战略洞察、市场机会、竞争动态、前瞻含义。
- **学术**（综述、实证、文献回顾）：优先研究缺口、方法论矛盾、理论张力、可定位于既有工作之上的新贡献角度。
- 文体不明时，产出中性洞察，兼顾战略与学术两面。

**每条洞察记录**：
- Insight：推断出的模式，一句话
- Derived From：维度引用（如 Dim02、Dim07）+ 支撑证据簇（Route C/D 含文件引用）
- Rationale：洞察如何从证据涌现
- Implications：潜在影响与意义
- Confidence：high / medium / exploratory

### 行动洞察（Actionable Insight，可选但推荐）[^storm]

当用户上下文提供了角色信息（如"我是投资者""帮我做采购决策""作为产品经理我需要判断…"），或研究主题明显指向某类决策者时，额外提炼 **1–2 条行动洞察**——不只告诉你"发现了什么"，而是告诉你**"基于这些发现，你应该做什么不同的事"**：

- **Action Insight**：作为 [角色]，基于全部证据，你应该采取的具体行动（一句话）。
- **Rationale**：为什么常规做法可能忽略了本次研究揭示的关键信号。
- **Confidence**：high / medium / exploratory。

格式范例：**"作为 [投资者]，你不应该只关注 [市场规模增速]，而应该盯紧 [单位经济性拐点信号]，因为本次查找发现 [核心数据] 表明前者的叙事阶段已接近尾声，后者才是下一阶段的分化关键。"**

若用户未显式指定角色但可从上下文推断（例如提问语境为"我在准备投资决策""我们公司想进入这个赛道"），主动推断并标注"角色为基于上下文推断"。

**规则**：不得重复既有发现；必须源自跨维度比对；避免无证据支撑的臆测；**至少 5 条洞察**（含行动洞察）；每条用内联 `[^id]` 引用支撑证据。

**输出**：保存到 **`{workspace}/research/{topic}_insight.md`**。这是整个研究的核心综合，是报告写作的首要输入。

## Phase 7：报告组装与交付

**目标**：把所有研究产物组装为最终交付文档。

**流程**：

1. **核对产物齐全**（均在 `{workspace}/research/` 下）：`{topic}_dim{NN}.md`（全部维度）、`{topic}_cross_verification.md`、`{topic}_insight.md`；Route C/D 加 `{topic}_file_analysis.md`；Route A 加 `{topic}_wide{NN}.md`。
2. **确定文体**：行研/市场/咨询/政策 → 报告体；学术综述/文献回顾 → 论文体。以 `assets/report_template.md` 为骨架。
3. **净化动态内容**：在将各维度产物、文件分析、交叉验证结果合并为最终报告之前，所有来自检索结果或文件摘录的动态文本字段（Claim、Excerpt、Source、URL、脚注定义文本）必须经过安全净化：
   - 转义 Markdown 元字符（`|` `&` `<` `>`）
   - 过滤可疑 URL 协议（`javascript:` `data:`）
   - 对表格单元格做 CSV 公式注入防护（`=` `+` `-` `@` 前缀保护）
   - 可运行 `python3 scripts/sanitize_markdown.py --file <path>` 逐文件处理，或从 `scripts/sanitize_markdown.py` import 净化函数在合并逻辑中调用。若不能执行脚本，按 `references/evidence-pipeline.md` 中「动态内容安全净化」规则表手工处理，结果一致。

4. **组装报告**，必须：
   - 纳入 Phase 6 洞察（报告体设独立"洞察"章节；论文体织入讨论/贡献章节）。**即使用户要求更短格式也不得省略洞察。**
   - 明确区分**已验证发现 / 冲突区 / 派生洞察**三类内容。
   - 保留全部 `[^id]` 溯源。
5. **引用去重与编号**：可运行 `scripts/dedup_citations.py {workspace}/research/` 按 URL 去重、统一编号、生成合并参考文献列表；若不能执行脚本，按下方"溯源契约"手动去重。
6. **时间校验**：若用户指定了时间范围，交付前核对关键数据与日期落在该范围内。
7. **格式**：交付 Markdown；若需 Word/PDF，用户未指定时**默认 Word**。若平台提供文档格式转换能力则调用之，本 skill 只负责产出结构化 Markdown。

## 溯源契约（贯穿全程，不可协商）

所有产物统一使用**标准 Markdown 脚注**：

- 正文处：`[^id]` 标记。
- 文件末尾：`[^id]: 标题. 日期. URL` 定义。
- 文件来源证据（Route C/D）可用 `[^id]: 文件名, 章节` 替代 URL。

**id 规则**：为每个 URL 选一个**短而稳定**的 id，同一 URL 在所有文件里复用同一 id。例如某来源第一次用 `[^gov1]`，后续引用同一 URL 仍用 `[^gov1]`。

**去重规则**：合并阶段按 URL 去重——同一 URL 的多个 id 归并为一个，按正文首次出现顺序分配显示编号。**不要**在交付时把脚注改成裸上标数字，**不要**把定义抽到单独列表后丢弃内联标记。

**示例**：
```
研究显示 2025 年市场规模达 120 亿元 [^idc1]，但另一来源给出 95 亿元 [^ana2]（冲突区，见交叉验证）。

[^idc1]: 中国 XX 行业白皮书. 2025-03. https://example.gov.cn/report
[^ana2]: XX 咨询市场报告. 2024-11. https://example.com/analysis
```

## 输出总则

- 洞察必须进入最终文档，不得因缩短格式而省略。
- 所有输出含 `[^id]` 引用。
- 最终文档清晰区分：已验证发现、冲突区、派生洞察。
- **Route C**：引用指向文件名与章节（非 URL），报告须声明"仅基于所提供文件"。
- **Route D**：引用须区分文件来源证据与外部检索证据。

[^storm]: Yijia Shao et al. "STORM: Synthesis of Topic Outlines through Retrieval and Multi-perspective Question Asking." NAACL 2024. https://storm.genie.stanford.edu/
